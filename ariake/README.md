# 有明 混雑モニター

有明エリア（東京ビッグサイト・有明アリーナ・有明ガーデン・各駅など）の
**いまの混雑と、3日先までの混雑予測**を1画面で見るためのツール。

対象利用者は「有明の住民」と「これから有明に行く人」。
住民には “いつ出かけると詰まらないか”、来訪者には “どの駅から入ると空いているか” を出します。

```
ariake/
  collect.py          収集 → 予測 → ariake.json 書き出し（これを叩くだけ）
  forecast.py         予測エンジン（到着/退場カーブ × 波及率 × 天候 × 祝日）
  config.py           スポット定義・影響度・事前分布（調整はここ）
  store.py            SQLite (ariake.db)：イベント/観測/天気/運行情報
  sources/            データソース別コレクタ
  manual_events.json  手入力イベント（スクレイパの取りこぼし対策）
  DATA_SOURCES.md     使えるデータソースの棚卸し（重要）
../ariake.html        ダッシュボード（ariake.json を読むだけの静的ページ）
```

## 使い方

```bash
pip install -r requirements.txt
python ariake/collect.py        # ariake.json を更新
python -m http.server 8080      # → http://localhost:8080/ariake.html
```

GitHub Actions（`.github/workflows/ariake.yml`）が1時間ごとに実行し、
`ariake.json` をコミットするので、常時稼働のPCは不要です。
（private リポジトリの Actions 無料枠 2,000分/月に収めるため毎時実行。
予測は3日先までなので、30分刻みにしても得られる情報は増えません）

## 0円で始める

有料APIを一切使わない構成です。**これが既定**で、追加設定は要りません。

| 使うもの | 費用 |
|---|---|
| 各会場のイベントスケジュール（スクレイピング） | ¥0 |
| 気象庁 予報JSON | ¥0（キー不要） |
| holidays-jp 祝日 | ¥0（キー不要） |
| GitHub Actions（毎時・月約1,080分） | ¥0（private の無料枠 2,000分/月 内） |
| ODPT 運行情報 | ¥0（無料登録すれば使える。未登録なら自動スキップ） |

有料の BestTime / Routes API はキーが無ければ**自動でスキップ**され、
イベント由来の予測だけで動きます。

> ⚠️ **GitHub Actions の `schedule` はデフォルトブランチ（main）でしか動きません。**
> 作業ブランチに置いたままだと自動実行されないので、main にマージしてください。

初回実行後は、ダッシュボード下部の「イベント取得」欄で
**会場ごとの取得件数**を確認してください。`0件⚠` が出た会場はサイト構造が
変わっているので、`config.EVENT_SOURCES` の URL を直すか、
`manual_events.json` に手入力してください。

## APIキー（任意・未設定でも動く）

| 環境変数 | 用途 | 取得先 |
|---|---|---|
| `ODPT_TOKEN` | ゆりかもめ／りんかい線の運行情報 | https://developer.odpt.org/ （無料） |
| `BESTTIME_API_KEY` | 混雑実測・人気時間帯カーブ | https://besttime.app/ （有料） |
| `GOOGLE_MAPS_API_KEY` | 道路の渋滞込み所要時間 | Google Cloud（従量課金） |

GitHub Actions では Settings → Secrets に同名で登録すれば自動で使われます。
**未設定のソースは自動でスキップ**され、残りのデータだけで予測が動きます。

### BestTime のコール数を制御する

クレジット課金なので、`config.BESTTIME` で呼び出しを厳密に絞っています。

```python
BESTTIME = {
    "hours": (11, 21),          # 11〜21時だけ
    "interval_hours": 2,        # 2時間おき (11,13,15,17,19,21時)
    "forecast_every_days": 7,   # 平常カーブは週1回だけ取り直す
    "monthly_credit_cap": 6000, # 月間上限。超えたら自動停止
    "kinds": ("facility", "venue"),   # 駅は対象外 (施設向けサービスのため)
}
```

現在の設定での月間リクエスト数:

| 内訳 | 計算 | 月間 |
|---|---|---|
| ライブ混雑 | 26施設 × 6回/日 × 30日 | 4,680 |
| 平常カーブ | 26施設 × 週1回 | 111 |
| **合計** | | **約4,800**（上限 6,000） |

同じ時間帯に2回走っても1回しか引かないガードを入れてあるので、
Actions の実行間隔を短くしても BestTime の費用は増えません。

消費数は `ariake.json` の `source_status` に `credits_this_month` として出ます。
上限に達すると自動停止し、翌月にリセットされます。
時間帯・間隔・対象を変えれば、そのまま費用が線形に増減します。

## 予測のしくみ

```
混雑度(0-100) = 平常値 × 天候係数 × 祝日係数 + イベント負荷 (+ 運行トラブル)
```

- **平常値**：①人気時間帯データ → ②自前の観測実績 → ③事前分布、の優先順で採用。
  観測が貯まるほど②に置き換わり、精度が上がります。
- **波及率**：`config.INFLUENCE` に明示した組み合わせが最優先。書かれていない
  施設には**距離減衰による既定値**が使われます（推測なので上乗せ上限つき）。
- **イベント負荷**：推定来場者を「到着カーブ」と「退場カーブ」に分解し、
  会場は滞在者数、駅・道路はその時間の流量、商業施設は滞在＋終演後の流入、
  として `config.INFLUENCE` の波及率で各スポットに配分します。
  これで「終演直後に駅だけ跳ねる」挙動を再現しています。
- **根拠**：各時間帯のスコアには寄与要因（どのイベントの何ピークか）が付き、
  ダッシュボードのセルにカーソルを当てると表示されます。

## 調整したいとき

| やりたいこと | 触る場所 |
|---|---|
| スポットを足す | `config.SPOTS` と `config.INFLUENCE` |
| 会場の波及の強さを変える | `config.INFLUENCE` |
| イベント規模の見積りを変える | `config.EVENT_SCALE_KEYWORDS` |
| 取りこぼしたイベントを足す | `manual_events.json` |
| 取得先サイトを足す／直す | `config.EVENT_SOURCES` |
| BestTime の呼び出し頻度・上限 | `config.BESTTIME` |
| 会場から離れた施設への波及の強さ | `config.SPILLOVER_*` と各スポットの `spillover_scale` |

## 注意

- 混雑度は 0〜100 の**独自推定値**で、実測人数ではありません。
- Google マップの「混雑する時間帯」は公式 API で提供されていません。
  詳細と代替手段は [DATA_SOURCES.md](DATA_SOURCES.md) を参照。
